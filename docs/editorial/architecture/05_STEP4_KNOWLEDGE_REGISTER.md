# Step 4 · Knowledge register format

*Implementation architecture, step 4 of 6 · 21 September 2026 · design authority: `CANONICAL_EDITORIAL_MAP_v1.md` §8–§9 · entities: `01_STEP1_TYPED_ENTITIES.md` (E-18) · stage contracts: `03_STEP2_STAGE_CONTRACTS.md` · storage: `04_STEP3_STORAGE_AND_RUN_TRACE.md` (patch S3-R1)*

This document fixes how knowledge records, check records, probe families, vocabularies and the default strength ladder are written, stored, validated, loaded into a run, expired and changed.

It resolves **U-4** (the wording of the default strength ladder) and sets the defaults for **OPEN-23** (expiry periods by knowledge class).

**Out of scope:** migrating the map's existing K-* records into files (Step 5/6). No implementation code.

---

## 0. Requirements this format must meet

| # | Requirement | Source |
|---|---|---|
| Q1 | A person without code and without an AI can open, understand, edit and put back any record | Project rule "how we write docs" (Valeria's requirement): plain markdown, one topic per file, autonomy |
| Q2 | A run can load records deterministically, with a version and a digest, and prove which records reached which stage | Step 2 §0.7 (`stage_routing`); Step 3 §4.1 (input versions) |
| Q3 | Every record has exactly one status and exactly one tier. The detection method of a check is recorded separately from its rule status | Map §8.1; I-11; patch history |
| Q4 | Conditions (`applies_when`) never refer to labels | I-10; AD-07 |
| Q5 | Soft signals have no thresholds, and research findings do not become hard checks, without owner approval | I-12, I-13 |
| Q6 | Platform knowledge expires and is demoted automatically | Map §6.2 |
| Q7 | Status changes happen only offline, by the keeper | I-02 |
| Q8 | The register is committed to a public repository | Step 3 P9 |

**Design consequence of Q1 + Q2.** Records use the format client documents already use (`clients/never_blank/lenses/*.md`, `streams/*.md`): a markdown file with a **short front-matter block** for the machine fields, and plain prose sections for everything a person reads. The keeper has already been editing documents in this format. A validator (§8) catches mistakes, so a person editing by hand cannot silently break a run.

## 1. What lives where

| Kind | Location | Edited by |
|---|---|---|
| Universal knowledge records (tiers 0–6, A): editorial, platform, evidence, process | `knowledge/records/<family>/<K-ID>.md` | Keeper (Sveta, Lera) |
| Check records (V-P*, V-T*, V-S*) | `knowledge/checks/<V-ID>.md` | Keeper; a hard-status change needs owner approval (Q5) |
| Probe families (`K-TEMPT-*`, U-1) | `knowledge/records/tempt/<K-TEMPT-ID>.md` | Keeper |
| Closed vocabularies: features, reason categories, label vocabulary, stage and field names | `knowledge/vocab/<name>.md` | Keeper; a new term needs a matching code change |
| Default strength ladder (U-4) | `knowledge/ladders/default.md` | Keeper |
| **Client rules** (tier 2) and client candidate rules | **Stay in the client folder**, `clients/<client>/…`, in the existing lens/stream format, with the front-matter fields from §2.2 added | Client setup (Client + Never Blank) |
| Register index | `knowledge/REGISTER.md`, generated by code from the files and never edited by hand | Code |

**Why client rules stay with the client.** The Client Contract is already the authority for client rules, and `client_contracts.py` already loads it. Putting tier-2 rules into a shared register would mix clients and create two authorities for one rule.

The register holds universal knowledge. The precedence engine reads both sources and applies map §5.

## 2. Knowledge record format

### 2.1 Example

```markdown
---
id: K-DST-LI-03
version: 2
status: candidate
tier: 4
evidence_class: VEND
confidence: low
verified_on: 2026-09-21
review_by: 2026-12-21
supersedes: K-DST-LI-03 v1
---

# External link in the body of a LinkedIn post

## Statement
Vendor data associates a link in the body of a LinkedIn post with lower
reach than the same post without it.

## Applies when
destination is linkedin

## Influences
S-10 adaptation: where the cross-destination link goes.
S-13 soft signal V-S10.

## Conflicts
None known.

## Source
<citation>; see research report "AI content on Meta and Telegram", section …

## Change log
- v2, 2026-09-21: confidence lowered from medium to low (keeper, from queue item KQ-…)
- v1, 2026-09-21: created from Knowledge Map v0.1
```

*The block above illustrates the format of a record file. It is not code.*

### 2.2 Fields

**Front matter** (machine fields, one line each):

| Field | Values | Rule |
|---|---|---|
| `id` | `K-<FAMILY>-<n>` | Stable across versions. Never reused |
| `version` | integer | +1 on every change to anything below the front matter or to status, tier or confidence |
| `status` | see §2.3 | Exactly one |
| `tier` | `0a` `0b` `0c` `1` `2` `3` `4` `5` `6` `A` | Exactly one; must be allowed for the status (§2.3) |
| `evidence_class` | `REPO` `RES` `PLAT` `VEND` `OBS` `CLIENT` `OWNER` `NBX-engine` `NBX-map` `INF` | One or more, comma-separated |
| `confidence` | `high` `medium` `low` | |
| `verified_on` | date | Required for `K-DST-*` and for every record whose class includes `PLAT` or `VEND` |
| `review_by` | date | Required for everything. Default by class (§5) |
| `supersedes` | previous `id vN` | Empty on v1 |
| `approved_by` | person and date | Required only for `invariant` and `approved-rule` status (Q5) |

**Body sections** (plain prose, fixed headings):

| Heading | Content | Required |
|---|---|---|
| `# <title>` | Human title | Yes |
| `## Statement` | What the record says, in one short paragraph | Yes |
| `## Applies when` | A condition in the controlled grammar (§4), or `always` | Yes |
| `## Influences` | Which stages and which entity fields it may shape (Step 2 names) | Yes |
| `## Conflicts` | IDs of records it conflicts with, and how precedence resolves each, or "None known" | Yes |
| `## Source` | Citations; for `NBX-*`, the run or experiment reference | Yes |
| `## Notes` | Anything a person needs: caveats, examples, what not to do | No |
| `## Change log` | One line per version: what changed, who, why, from which queue item | Yes |

### 2.3 Status vocabulary and allowed tiers

| Status | Meaning | Allowed tiers | Who may set it |
|---|---|---|---|
| `invariant` | Must always hold; violating it is a failure | `0a`, `0b`, `0c`, `A` | Keeper, with owner approval (`approved_by`) |
| `approved-rule` | A hard rule with authority: hard platform policy (tier 1), or an approved client rule (tier 2, in the client folder) | `1`, `2` | Keeper with owner approval (tier 1); client setup (tier 2) |
| `descriptive` | Describes how things tend to work; a strong input, never mandatory | `3`, `4`, `5`, `6` | Keeper |
| `candidate` | A plausible practice not yet validated; a weaker input | `3`, `4`, `5`, `6` | Keeper |
| `weak-candidate` | **Set only by the loader** when a candidate or descriptive record is past `review_by` (§5). Never written in a file. Demotion semantics in §5.1 | as the file's tier | Loader (automatic) |
| `retired` | Kept for traceability; never loaded into a run | any | Keeper |

**A client's unapproved rule** is written in the client folder with `status: candidate` and `tier: 3`, per map §5 rule 1. Approval changes it to `approved-rule`, `tier: 2`.

## 3. Check record format

Checks (map §9) are records of their own kind, because they need a route table and an explicit criterion.

**Front matter:**

| Field | Values |
|---|---|
| `id` | `V-P01` … `V-S10` |
| `version` | integer |
| `class` | `H` (hard) / `S` (soft) |
| `rule_status` | `invariant` / `approved-rule` / `candidate` |
| `method` | `code` / `model-explicit-criterion` / `code+model` |
| `threshold` | `none` by default. A value is allowed only with `approved_by` (I-12) |
| `approved_by` | Required when `class: H` and the rule came from research (I-13), and whenever `threshold` is not `none` |
| `review_by` | date |

**Body sections:**

- `## Rule`: what must hold.
- `## Criterion`: the exact explicit criterion the model call uses, written as a question with pass/fail conditions. For code checks, a plain description of what code compares.
- `## Enforces`: the K-* records or invariants behind it.
- `## Route`: a table of finding → route → counter → outcome at exhaustion. It must match Step 2 exactly, including the V-T01 and V-T08 branches (patch R2).
- `## Branch criterion`: V-T01 and V-T08 only. The question that decides `writer` versus `plan`, and the default when uncertain (plan).
- `## Change log`.

**Soft checks** (`class: S`) always have `threshold: none` unless an owner-approved threshold is recorded. Their results are hints and portfolio signals only.

## 4. The `Applies when` grammar

A condition is a short line of controlled English that code parses and people can read.

**Terms** (each must exist in `knowledge/vocab/`):

| Term family | Examples | Refers to |
|---|---|---|
| `feature <name> is <value>` | `feature documented_case is yes`; `feature figure_provenance is third_party` | E-05 |
| `boundary has <fact>` | `boundary has contested_assertion`; `boundary has counter_evidence`; `boundary has at least 2 admissible interpretations` | E-09 facts computed by code |
| `destination is <name>` | `destination is instagram` | E-12 |
| `format is <name>` | `format is carousel` | E-14 |
| `strategy <field> is <value>` | `strategy reveal is delayed`; `strategy concession is present` | E-13 fields. Allowed only in records that influence S-09 … S-13 |
| `audience <attribute> is <value>` | `audience english_level is global` | Audience Profile |
| `always` | — | — |

**Connectives:** `and`, `or`, `not`, parentheses.

**Forbidden, and rejected by the validator:**

- any term from `knowledge/vocab/labels.md`: `material_label`, strategy labels, path names such as "Teardown", "Finding", "Scene";
- any free text outside the grammar.

This is how Q4 / I-10 is enforced at the source: a record cannot be conditioned on a label because the parser has no term for it.

**Time of evaluation.** A condition is evaluated by code at the stage it influences, against the entity versions that stage reads. The result (true/false per record) goes into the StageRecord's routing evidence. A model is never asked whether a condition holds.

## 5. Expiry and demotion (OPEN-23 defaults)

**Default `review_by` periods by class.** These are tunable parameters; the rule that expiry is automatic is architecture.

| Record class | Default period |
|---|---|
| Platform ranking and behaviour (`K-DST-*`, tier 4, `VEND` / `PLAT`) | 90 days |
| Hard platform policy (tier 1) | 90 days |
| Editorial practice from research (`RES`, tier 3) | 365 days |
| Observational (`OBS`, `NBX-*`) | 180 days |
| Invariants (tiers 0a–0c, A) | 365 days (review, not expiry) |
| Probe families (`K-TEMPT-*`) | 365 days |
| Check records | 365 days |

**What happens when `review_by` passes**, decided at load time and recorded in every KnowledgeRef as "effective status":

| Status in the file | Effective status after expiry | Why |
|---|---|---|
| `descriptive`, `candidate` | `weak-candidate` | Map §6.2: old knowledge is not used as a strong input |
| `approved-rule`, tier 1 (hard platform policy) | **Stays enforced**, flagged `expired_review` | Dropping a hard rule because nobody re-checked it would be the unsafe direction. ARP "safest admissible" means the stricter rule |
| `invariant` | Stays in force, flagged `expired_review` | Invariants do not lapse |
| Check records | Keep their rule status, flagged | Same reasoning |

### 5.1 What `weak-candidate` may and may not do (patch S4-R1)

A `weak-candidate` does **not** behave like its unexpired source status. It keeps its tier, but it has these executable limits:

1. **It cannot by itself cause an exclusion, a `REPLAN` or a `SKIP`.**
   - At S-09, a candidate strategy is never excluded solely because it conflicts with a weak-candidate.
   - At S-11 and S-13, no route is triggered solely by a weak-candidate.
   - If a weak-candidate is the only record behind an exclusion or route, that exclusion or route is not taken. The conflict is recorded as a hint instead.
2. **It loses to any non-expired record of the same tier,** whatever the confidences. Within tier 3, the order is therefore: non-expired by confidence, then weak-candidates by confidence.
3. **It is usable only as supporting soft input or as a late tie-breaker.** In S-09 it can act only after the §7.3 tie-breakers that rest on evidence, destination and interpretation risk. That is, at the portfolio/cost end, as a soft preference.
   - **Exception:** it counts at its original weight when a non-expired record of the same or a higher tier points the same way ("reinforced"). The reinforcing record is cited in the KnowledgeRef.
4. **Recording.** Every KnowledgeRef records both the **file status** and the **effective status** (`weak-candidate`), and whether the record was reinforced. Every PrecedenceApplication that involves a weak-candidate records its effective status, so the trace shows that demoted knowledge could not win a conflict.

### 5.2 Expiry review items

**Expiry and review queue items are produced by the Knowledge Maintenance job, not by a run** (patch S4-R1).

- The job is **offline and scheduled**, for example daily. It scans the register and client rule files for records past `review_by`, or within a warning window before it. It writes one KnowledgeQueueItem per record per expiry, never one per run.
- It does **not** depend on a publication or a run happening, so expiry review continues even when nothing is published.
- It runs outside every production run and **never blocks one**. If it fails, the next scheduled run retries. Production runs still apply §5 demotion at load time, independently of the job.
- **The run's loader does not write queue items.** It only computes effective status.

## 6. Probe families (K-TEMPT, U-1)

A probe family is a knowledge record (§2) in `knowledge/records/tempt/`, with two extra required body sections:

| Section | Content |
|---|---|
| `## Probe` | The question the S-04 probe call asks for this family, e.g. "Is there a reading that transfers the case's outcome onto the configured reader without evidence scoped to that reader?" |
| `## Real examples` | At least one real engine output that fell into this family, cited by sample-pack or run reference |

- **Status** is `descriptive` or `candidate`, **tier 3**. Families influence S-04 only.
- **Initial families**, from Step 2 U-1: transfer to reader; benefit inflation; invented scene; causal overreach; generalization from a single case; forecast stated as fact; burden inflation.
- **New families** are proposed by the U-1 feedback loop (a V-T02 finding that matched nothing) through the knowledge queue. The keeper adds them offline.

## 7. Default strength ladder (U-4 resolved)

**Decision.** The universal default ladder has four levels, worded as what the evidence shows, so that a writer can phrase a claim at the right strength.

| Level | Wording | Evidence that reaches it |
|---|---|---|
| 1 | **Reported**: "X says / reports …" | One source, attributed; nothing independent |
| 2 | **Documented in a case**: "in this case, …" | A primary document or a documented single case (named company, record, filing) |
| 3 | **Corroborated**: "several independent sources show …" | Two or more independent sources agree; no material contradiction |
| 4 | **Established**: "across … , …" | **Either** authoritative statistics that directly measure the thing claimed (e.g. an official statistical series on exactly that quantity), **or** convergent or systematic evidence across multiple cases: several independent studies agreeing, a systematic review, data spanning many cases. **One individual study, however well-designed, reaches level 3 at most** (patch S4-R1) |

**Rules on top of the ladder:**

- An interpretation's strength ≤ the lowest strength among its supporting evidence claims (Step 1 E-08).
- A `forecast` interpretation is capped at level 2, whatever its supports. A forecast is never "established".
- A `generalization` from a single case is capped at level 2, which is also a probe family.
- **A client ladder** (declared in the contract, as `claim_strength_ceiling` today) is used for that client's runs (AD-10), under constraints (patch S4-R1):
  - It may **rename** the universal levels, e.g. "observed on one shop floor" for level 2.
  - It may **restrict further**, e.g. merge levels 3 and 4, or declare a lower top level.
  - It may **never permit a stronger assertion than the universal ceiling for the same evidence pattern.**
  - To make that checkable, every client level must declare which universal level it **maps to**. Its effective ceiling is the minimum of the client level and the universal level reached by the evidence. A client level can never lift a claim above what the universal ladder allows for that evidence.
  - The client ladder must be ordered from weakest to strongest and have at least two levels.
  - The validator rejects a client ladder that lacks mappings, is not monotonic, or maps a level to a stronger universal level than its position allows.

**Alternatives considered**

| Option | Why rejected |
|---|---|
| Three levels (weak / medium / strong) | Too coarse to separate "one documented case", the most common Never Blank material, from "several sources" |
| Numeric strength | False precision; nobody can tell a writer what 0.6 means |
| Separate ladders for evidence and interpretation | Rejected in AD-10: the minimum rule needs one scale |

**Location:** `knowledge/ladders/default.md`, in the §2 format with `status: invariant`, `tier: A`.

## 8. Validation (the safety net for hand edits)

A validator runs in CI on every change to `knowledge/` and to the client folders' rule files, and again at run start. It **rejects** a change if:

1. front matter is missing a required field, or has an unknown value;
2. status and tier are not an allowed pair (§2.3);
3. `invariant`, `approved-rule` tier 1, a hard check from research, or any non-`none` threshold lacks `approved_by`;
4. `Applies when` does not parse, or uses a label term;
5. `Influences` names a stage or field that does not exist in Step 2;
6. a check's `## Route` table differs from Step 2;
7. `id` already exists in a different file, or `version` did not increase when the body changed;
8. `K-DST-*` lacks `verified_on`;
9. a client ladder lacks a universal-level mapping for every level, is not monotonic, or could permit a stronger assertion than the universal ladder for the same evidence (§7);
10. a file contains text matching credential patterns (Q8).

**At run start**, a validation failure means the run does not start: `SKIP` at signal scope, reason `knowledge_register_invalid`. That is fail-closed and needs no human during the run. The broken record is fixed offline.

## 9. Loading into a run

1. **Register version** = the git commit of the `knowledge/` tree plus a digest over the loaded files. It is recorded in the manifest's input versions (Step 3 §4.1).
2. **Retired records are not loaded.** Expired records get their effective status (§5).
3. **Selection per stage:**
   - a record is **eligible** for a stage if the stage is in its `Influences`;
   - it is **applicable** if its condition evaluates true against that stage's inputs.
   Applicable records are routed to the stage and declared in `stage_routing`. `stage_routing` then proves containment in the actual request.
4. **KnowledgeRef** (Step 1) records ID, version, tier and **effective** status at the time of use.
5. **Precedence** uses tier first, then confidence within tier 3 (map §5). Every application is written to the PrecedenceLog (U-3).
6. **Size discipline** (patch S4-R1).
   - **Mandatory knowledge is never truncated.** When applicable, these always reach the stage in full: every tier `0a`, `0b`, `0c` and `A` record; every tier `1` and tier `2` rule (including the client's approved rules); every hard (`class: H`) check record the stage applies.
   - **Only** `descriptive`, `candidate` and `weak-candidate` records may be reduced for context size. They are cut in tier order, then by confidence, weak-candidates first. The excluded remainder is recorded in the StageRecord.
   - **If the mandatory set alone exceeds the request capacity,** the stage fails closed **before** the model call. The call is not made, and the StageRecord records `mandatory_knowledge_exceeds_capacity` with the sizes. The outcome is `SKIP` at the stage's scope (destination for S-08…S-13; signal or unit for earlier stages). No incomplete hard-policy surface is ever sent.
   - `stage_routing` containment proves, per request, that every mandatory record was present.

## 10. Changing knowledge (offline only)

| Change | Who | Requirement |
|---|---|---|
| Edit a statement, source, notes, condition | Keeper | New version; change log line; validator passes |
| `candidate` ↔ `descriptive`; confidence change | Keeper | Based on queue items or evidence; change log cites them |
| Anything → `invariant`, or a new tier-1 `approved-rule` | Keeper **with owner approval** | `approved_by` filled (I-13) |
| A soft check gets a threshold | **Owner decision** | `approved_by`; I-12 |
| Retire a record | Keeper | `status: retired`; kept in place |
| A new vocabulary term | Keeper + developer | The term and its code meaning ship together; otherwise the validator rejects records using it |

Platform metrics never change a file. They create queue items (Step 3 §3.2), and the keeper decides.

## Кратко по-русски (для Светы)

- **Как записывается знание системы.** Каждая запись — отдельный обычный markdown-файл: сверху несколько служебных строк (номер, статус, уровень, даты), ниже понятные разделы «Что утверждается», «Когда применяется», «На что влияет», «Источник», «История правок». Точно так же уже устроены документы клиента, так что ты и Лера можете править их без разработчика и без ИИ.
- **Правила клиента остаются в папке клиента,** как сейчас. В общем реестре лежит только общее знание.
- **Защита от ошибок при ручной правке.** Проверка отклоняет файл, в котором что-то сломано, например условие написано через метку «Разбор» или у записи два статуса. Если реестр сломан, прогон просто не начинается.
- **Устаревание.** Знание о площадках действует 90 дней. Потом слабые записи автоматически теряют вес, а жёсткие правила площадок продолжают действовать (так безопаснее), и тебе в очередь приходит напоминание их перепроверить.
- **Шкала силы утверждений:** «сообщается» → «подтверждено в одном случае» → «подтверждено несколькими источниками» → «установлено». Прогноз и обобщение из одного случая выше второй ступени не поднимаются.
- **Что нужно от тебя или владельца.** Сделать правило обязательным или назначить порог можно только с согласия владельца. Это записывается в самом файле.
